# v0.1-research 可复现发布设计

日期：2026-07-26

## 目标

把已经通过第 1 至第 5 周阶段门的 A 股研究工程整理为一个可审查的
`v0.1-research` 发布版本。一个没有现有 `data/`、`outputs/backtests/`、
`outputs/experiments/` 和 `outputs/reports/` 的干净 Git 工作树，必须能够只依赖仓库内冻结输入：

1. 安装锁定环境；
2. 验证冻结输入的 SHA-256；
3. 重新生成 20 个正式基准运行；
4. 重新生成 30 个第 5 周 SMA 候选运行；
5. 重建风险报告和第 5 周实验；
6. 将全部身份与发布清单逐项比对；
7. 返回机器可读的成功或脱敏失败结果。

发布完成不代表策略有效、能够实盘成交或能够盈利。

## 已批准的范围

- 标的保持 10 个，不扩充股票池；
- 证券类型仍只包含普通沪深主板股票和境内股票型宽基 ETF；
- 策略仍只包含 Buy & Hold、冻结 SMA(20) 和第 5 周 SMA(10/20/60) 候选；
- 数据仍为 `research_approx` 冻结快照；
- 继续使用 Python 3.11、AKShare、Backtrader、uv、pytest 和 Ruff；
- 继续采用原始成交价、指标价和涨跌停参考价三分流；
- 保留 T+1、整手、版本化费用、停牌、一字板保守拒单和现金红利会计规则。

## 明确排除

- 不接入券商、不提交订单、不增加自动交易；
- 不引入 Qlib、CrewAI、AutoGen 或新的策略族；
- 不实现共享现金组合、部分成交、滑点和成交量约束；
- 不支持创业板、科创板、北交所、ST、新股特殊阶段和退市整理期；
- 不把当前固定样本称为市场代表样本；
- 不因保留期结果不理想而调整周期、样本或选择规则。

## 方案比较与决定

### 方案 A：冻结输入加预期身份，干净环境重新计算（采用）

仓库保存约 1.4MB 的必要冻结输入和一份发布清单，不保存约 20MB 的重复运行输出。验收命令在
临时目录重新执行完整流水，并比较 20 个基准 run ID、30 个候选 run ID、风险 report ID 和
experiment ID。

优点是体积小、真正验证从输入到报告的重建能力，并能发现实现指纹、依赖、排序或默认参数漂移。
代价是验收时间高于只检查旧文件。

### 方案 B：提交全部历史输出（不采用）

能够离线查看所有 CSV，但主要证明“旧文件仍存在”，不能单独证明当前代码可以重建它们；同时会
让 Git 长期保存数百个重复输出文件。

### 方案 C：外部制品仓库（暂不采用）

适合未来 GitHub Release 或对象存储，但当前项目没有远程仓库。把 v0.1 的最低复现能力依赖于
外部链接，会增加失效和权限风险。

## 发布清单契约

`release_manifest.json` 使用规范 JSON，至少包含：

- `schema_version`：固定为 `1.0`；
- `release_name`：固定为 `v0.1-research`；
- `implementation_commit`：包含全部业务代码和验收器、但尚未加入发布清单的冻结提交；
- `python_version`、`akshare_version`、`backtrader_version`；
- `universe_id`、`calendar_id`；
- 10 个标的的行情 snapshot ID 和公司行为 snapshot ID；
- `input_files`：相对路径到 SHA-256 的完整映射；
- `baseline_run_ids`：以“标的＋策略”为键的20个精确 run ID；
- `candidate_run_ids`：以“标的＋SMA周期”为键的30个精确 run ID；
- `risk_report_id`；
- `week5_experiment_id`；
- `expected_counts`：标的、正式基准、候选和回放行数；
- `research_boundary`：固定声明研究、模拟、非实盘、非收益承诺。

清单本身采用内容规范化和严格字段白名单。未知字段、重复键、非小写 SHA-256、绝对路径、`..`、
软链接、硬链接、缺文件、多文件或哈希不一致全部关闭运行。

## 身份确定性契约

当前 `run_id` 已经是确定性身份，不含墙钟时间、进程 PID、UUID 或引擎全局订单号。它由以下字段
经 `json.dumps(sort_keys=True, separators=(",", ":"))` 规范化后计算 SHA-256：

- schema 和 Backtrader 版本；
- 按固定顺序读取的执行实现源码指纹；
- 冻结行情规范值摘要、行情 snapshot 和文件 SHA-256；
- universe、交易日历、费用政策和证券类型；
- 策略、初始资金、目标权重、SMA 周期和固定随机种子；
- 公司行为 snapshot、规范化版本和覆盖区间；
- 价格三分流版本和红利税边界。

`report_id` 先按“标的＋策略”排序全部正式运行，`experiment_id` 先按标的和候选周期排序，再使用
相同的规范 JSON 和 SHA-256。代码中的集合只用于相等性和唯一性验证；进入身份的序列必须显式
排序。单成员集合取值只能在已验证集合大小为1后使用。

第 6 周首先增加确定性契约测试：

- 同一冻结输入在两个全新输出根目录各运行一次，全部载荷和 run ID 逐字节一致；
- 相同20个运行以不同输入顺序构建报告，report ID 和载荷一致；
- 相同30个候选与基准以不同字典插入顺序构建实验，experiment ID 和载荷一致；
- 测试中冻结墙钟、PID并改变 `PYTHONHASHSEED`，身份不得变化；
- 任一实际身份字段变化时，对应身份必须变化。

如果这些测试失败，第 6 周停止在身份层，不继续生成发布清单。

## 一键验收命令

环境安装和研究重算分为两个安全阶段。首次在仓库根目录安装依赖：

```bash
./scripts/bootstrap_env.sh
```

该阶段在本地没有 uv 缓存时可能访问 Python 包索引，只负责取得 `uv.lock` 指定的依赖，不读取或
更新市场数据。依赖安装完成后执行：

```bash
./scripts/verify_v01.sh
```

脚本只负责：

1. 检查 `uv`；
2. 检查当前环境与 `uv.lock` 一致，不自动下载数据；
3. 调用 `uv run --no-sync aquant-release verify --project-root .`。

`aquant-release verify` 负责业务验收：

1. 验证清单与全部冻结输入；
2. 使用 `tempfile` 创建明确的临时项目根目录；
3. 复制必要配置、冻结输入和 universe；
4. 通过现有公共 CLI 或等价公共入口重建正式基准、风险报告、候选实验和回放；
5. 对比所有预期身份与数量；
6. 验证每个输出包的 artifact manifest；
7. 成功时 stdout 只输出一行 JSON；
8. 失败时 stderr 只输出脱敏 JSON，退出码非零。

验收器不得读取当前仓库中已有的正式 `data/` 或 `outputs/` 来代替发布夹具。测试将放入冲突文件
证明这一边界。

## 网络隔离

研究重算阶段必须完全离线。`aquant-release verify` 不调用 `aquant-data`、`AkshareClient.fetch`
或公司行为下载入口，只调用本地 snapshot、backtest、report 和 experiment 公共入口。

验收器在进入重算前安装进程级网络守卫，阻止 `socket.connect`、`socket.connect_ex`、
`socket.create_connection` 和 Requests 会话请求；任何尝试使用网络都转为固定错误码
`network_access_forbidden`。测试使用一个必定尝试连接的假入口证明守卫有效，并在网络函数被
替换为立即失败的条件下完成一次完整重算。

正式发布门还要在依赖已经安装后，用操作系统断网或等价的出站阻断环境执行
`./scripts/verify_v01.sh`。这里验证的是研究重算离线，不声称首次依赖安装在空缓存机器上也无需
网络。

## 冻结输入闭包

v0.1 的闭包定义为“本发布指定的20个基准和30个候选运行能够读取的全部项目数据文件”，不是未来
所有可能策略分支的文件并集。当前正式入口的闭包固定为：

- universe 文件；
- 行情 manifest 及10个正式 snapshot；
- 交易日历 manifest 及指定 calendar；
- 公司行为 manifest 及10个指定 snapshot；
- 代码内版本化费用政策和策略参数。

发布器从清单身份反向解析上述路径，不接受人工自由添加路径。临时项目根目录只复制这组白名单
文件；根目录原有 `data/` 和 `outputs/` 不挂载、不回退。验收期间记录应用在临时 `data/` 下的
读取路径，最终要求它们全部存在于 `input_files`；清单声明但未触达的文件也视为闭包不精确并
失败。未来新条件分支需要新文件时，必须更新发布夹具和清单，不能静默读取机器上的其他文件。

## 干净环境判定

第 6 周正式验收使用 `git archive` 或临时克隆形式构造只含 Git 跟踪文件的目录。在该目录中：

- 不存在当前机器的 `venv`、缓存和历史输出；
- 安装必须来自 `uv.lock`；
- `./scripts/verify_v01.sh` 必须成功；
- 重建结果必须与发布清单逐项一致；
- 再运行 369 项以上自动化测试和 Ruff；
- 归档验收日志和机器可读摘要，但不把临时运行目录提交 Git。

首次完整运行后，把当前 macOS 机器的实际耗时写入发布 README，格式为“参考耗时＋机器环境”，
并在成功 JSON 中记录 `elapsed_seconds`。在实测前不写猜测值；执行期间每完成数据验真、基准、
风险报告、候选实验和最终比对中的一个阶段，就向 stderr 输出一行不含路径的进度 JSON，便于区分
正常运行和卡死。

如果冻结输入能够验真、但重新计算的身份不一致，发布门失败。不得用更新预期 ID 的方式掩盖原因；
必须先判定是代码、依赖、非确定性、清单或输入错误。

## 测试设计

新增测试覆盖：

- 正确清单和冻结输入通过；
- 任一输入字节变化被拒绝；
- 绝对路径、路径穿越、软链接、硬链接和未知文件被拒绝；
- 重复键和未知清单字段被拒绝；
- 预期 run/report/experiment ID 被篡改时失败；
- 验收器不读取项目根目录已有 `data/` 和 `outputs/`；
- stdout/stderr 契约和错误脱敏；
- 研究重算阶段的任意网络访问被固定错误码拒绝；
- 实际读取的项目数据路径与 `input_files` 精确闭合；
- 重复执行得到相同 JSON 摘要；
- 改变字典插入顺序、`PYTHONHASHSEED`、墙钟和 PID 后身份保持稳定；
- 完整干净目录的端到端重建产生 20 个基准、30 个候选和100行回放。

端到端重建属于发布验收测试，不在每次普通单元测试中重复运行。普通测试使用最小夹具验证清单、
路径和身份逻辑。

## 发布门与标签

只有以下条件全部成立才允许创建 `v0.1-research` 标签：

1. 当前分支无已跟踪文件改动；
2. 全量 pytest、Ruff、`uv lock --check` 和构建通过；
3. 干净 Git 目录的一键验收通过；
4. 真实风险报告反向验证通过；
5. Claude Code 完成代码和文档复核；
6. `P0=0` 且没有未解决的 `P1`；
7. 发布报告明确列出所有负结果和不支持范围；
8. 标签指向实际通过验收的提交，不提前创建或移动标签。

标签是研究版本身份，不是实盘批准、投资建议或盈利证明。

`release_manifest.json` 不保存包含它自身的最终提交 ID，以避免自引用。最终发布提交由
`v0.1-research` 标签唯一指向；清单中的 `implementation_commit` 用于确认生成预期身份时使用的
业务代码版本。

清单不增加自签名或自引用哈希。Git 提交和标签用于固定清单版本，本地 SHA-256 用于发现损坏与
混用；能够同时改写仓库、标签和清单的攻击者仍可伪造内部一致结果。这是 v0.1 的明确安全边界，
不是遗漏，后续只有在引入外部只读存储或第三方签名时才升级。
