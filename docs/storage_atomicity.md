# 存储原子性边界

v0.1 的原始快照和 manifest 只支持 POSIX 本地文件系统。实现依赖 `fcntl`
文件锁、同目录硬链接发布、目录文件描述符和目录 `fsync`。这些假设用于避免
进程并发写入交错、覆盖已有快照和符号链接逃逸。

四标批次先写四个内容寻址快照，再通过 `append_batch()` 持有一次 manifest
锁、预检全部冲突，并用一次原子替换发布整批记录。manifest 是批次的事务
边界：写入、替换或目录 `fsync` 失败时，权威清单只能保持旧完整状态或新
完整状态，不能出现一至三条新记录。

快照阶段失败时，`data/raw` 可能留下未被 manifest 引用的内容寻址文件。
这些文件是未发布孤儿，重试时可以复用，但读取端不能把它们视为批次成员。
下游只能从 manifest 取得路径，并在读取前调用快照校验，重新检查 SHA-256、
常规文件类型和 `st_nlink == 1`。新快照取消写权限位，降低同用户误写风险；
同用户仍能重新加写权限，因此哈希复核不能省略。

如果快照已用硬链接发布，但对临时别名的删除失败，首次调用会明确报错。
后续重试只能清理同目录中匹配 `.snapshot-<32 位十六进制>.tmp`、与已发布
目标具有相同 inode 的遗留别名，并在删除后 `fsync` 目录。任何不在受控命名空间
中的外部硬链接仍会被拒绝，不会为了重试而放宽完整性检查。

manifest 数据文件在读取和追加前同样要求 `st_nlink == 1`。这能防止应用
把存在外部硬链接别名的清单当作可信事务边界，但不构成对抗同用户恶意
重写的外部信任锚。项目尚未使用独立签名、远程存证或可信时间戳；因此当同用户
同时重写快照、哈希和 manifest 时，本地检查无法提供独立的篡改证明。

当前不承诺以下环境具有相同的原子性或持久性语义：

- Windows；
- NFS 等网络文件系统；
- 同步云盘、对象存储挂载和其他虚拟化文件系统。

若项目迁移到上述环境，必须重新验证锁、硬链接、`O_NOFOLLOW` 和 `fsync`
的实际语义，未验证前不得将该环境产生的文件视为可信研究快照。
